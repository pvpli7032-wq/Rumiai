[Heading 2] 2. 后端建议（Part A）
[Normal] 总体判断：业务层（src/lib/<域>/）划分已经合格，不需要重写；问题全部在“入口层”——后台寄生在前台里、接口前缀分散、路由写法不统一。因此后端改造是重组入口，不动业务规则。同时不建议现在拆成两个仓库或两个服务：共享同一套 Prisma 与 lib、单机 SQLite、人手有限，拆分的维护成本大于收益；等到多人协作或多实例部署再议。
[Heading 3] A1 后台独立入口（阶段 1）
[Normal] 目标：后台成为独立“应用壳”，前台代码不再感知后台。
[List Paragraph] 新建路由组 src/app/(admin)/，其 layout.tsx 只渲染 AdminAccessProvider + AdminShell，不引入前台的 Sidebar、Topbar、MobileNav、MaintenanceNotice。
[List Paragraph] 把 (app)/admin/**、(app)/finance、(app)/moderation 的页面移动到 (admin) 下，URL 统一为 /admin/<域>：/finance → /admin/finance，/moderation → /admin/moderation。同一提交内必须删除旧位置（两个路由组下不能有相同路径）。
[List Paragraph] next.config.mjs 增加 redirects：/finance、/moderation 跳到新地址（先用临时跳转，稳定一个发布后改永久）。
[List Paragraph] 删除 app-frame.tsx 里 pathname === '/admin' ... 的后台分支及对 AdminShell、use-admin-access 的 import。注意：AdminShell 用到的 --app-height 变量原由 AppFrame 的 effect 写入，独立后依赖 globals.css 里的 100dvh 兜底，需在手机端实测。

[Normal] 验收：前台页面的组件树不再引用任何后台组件；/admin、/admin/finance、/admin/moderation 可打开且外壳正确；旧地址正确跳转；npm run typecheck、npm run test:admin:access、npm run test:admin:browser 通过。
[Normal] 后期选项（不在默认范围，需负责人批准）
[List Paragraph] 后台改用 HttpOnly Cookie 会话 + 服务端 layout 校验权限：项目已有 lib/auth-cookies.ts 先例。收益：未授权者拿不到后台前端结构，并可叠加二次验证（TOTP）。商业正式上线前建议做。

[Heading 2] 3. 前端建议（Part B）
[Normal] 总体判断：前台“简约”是继承来的默认骨架——灰黑 shadcn 配色加泰语原站布局。缺的不是组件数量，而是品牌层、内容层、信任层。前台与后台代码耦合很低（见第 1 章），因此可以放心按页面逐个改；真正要先动的是共享地基，且要最小化改动面。行业报道也提醒，AI 社交产品的普遍问题是角色语言重复、记不住上下文、玩法同质化、付费转化不及预期——商业化的重点是留存与转化，而不是堆功能。

[Normal] 要点：
[List Paragraph] 支付回调地址由 NEXT_PUBLIC_SITE_URL 拼出（order-service.ts 生成 notify_url 与 return_url），所以预发布实例下的订单会回调预发布域名，不会打到现网。
[List Paragraph] 回调域名白名单：支付渠道只登记了现网域名 lh.y-98.cn，预发布域名不在白名单内，渠道会拒绝其回调。因此预发布实例上的支付只验证到下单与验签，回调用本地模拟渠道验证；完整的支付与退款冒烟按决策 D10（已选方案 B）在现网进行。
[Normal] 决策 D10（已确定：方案 B）：负责人已选择不新增渠道白名单，改在现网 https://lh.y-98.cn 上用合成账号做小额支付冒烟。执行协议如下：
[List Paragraph] 时机：阶段 0 到 8 在预发布实例上全部通过后，由负责人把新版本部署到现网；部署完成后，执行 AI 才执行本冒烟。
[List Paragraph] 前置条件现网退款开关已开启且商户配置验证通过；负责人在现网后台给两个合成账号分别授予“财务经办员”与“退款审批员”角色（系统要求双人复核）；负责人已在服务器执行 npm run db:backup 备份现网数据库；选在低峰时段。
[List Paragraph] 流程：AI 用合成账号登录，选最小面额套餐（6 元档）下单，到达渠道支付页后截图并通知负责人；负责人在手机上扫码付款（AI 无法代付）；AI 核对回调到账：订单状态、金币流水、余额一致，重复回调不重复入账；AI 用两个管理员账号完成整单退款（申请、审批）；核对退款后的余额、流水与财务对账。
[List Paragraph] 限制：只创建和操作合成测试数据；不修改任何现网配置；不读取、不输出真实用户数据；不做压力或并发测试；单轮不超过 3 笔，建议 1 到 2 笔。
[List Paragraph] 收尾：测试结束后，由负责人撤销两个合成账号的管理角色并停用；合成用户账号走注销流程；所有测试订单号写入报告。
[List Paragraph] 须知：订单、退款与金币流水属于账务记录，不会被删除，会出现在财务报表与运营分析中；报告列出的测试订单号用于日后排除。
[List Paragraph] 停止条件：任何一笔的金额、金币数或余额对不上；回调迟迟未到账；退款失败或状态未知。出现任一情况立即停止，保持冻结，按原退款单号查单，向负责人汇报订单号，不得重复下单。

[Heading 3] 8.4 自测方式
[List Paragraph] 优先复用现有脚本（scripts/verify-*-browser.mjs 与 tests/*.test.mjs）；缺口用新增的 Playwright 脚本补齐，放在 scripts/e2e/，并在 package.json 增加 test:e2e:* 命令。
[List Paragraph] 执行顺序：服务与单元测试，然后浏览器脚本，然后 F、B、X 全链路旅程，最后汇总报告。
[List Paragraph] 失败处理：自行定位修复并重跑；同一问题连续修复 3 轮仍失败，则记录现象与已尝试的做法，继续其他项，最终在报告里列出。
[List Paragraph] 资金类用例（F6、B8）结束后运行 test:payments:reconciliation 对应的对账检查：订单数、流水、余额一致，负余额为 0。
[List Paragraph] 每项保存截图、控制台日志与请求日志（均已脱敏）到 artifacts/selftest-<日期>/。
