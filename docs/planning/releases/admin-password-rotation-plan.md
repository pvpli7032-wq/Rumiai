# 生产管理员密码轮换方案

> 现状缺口：生产管理员密码为 `123123`（HANDOFF 第 6 节第 1 条），`/admin` 公网可达，属高危弱口令。
> 本文档只写方案，不执行。执行需 team-lead 与 security-lead 批准，并另开变更记录。

## 1. 背景与风险

| 项 | 现状 |
|---|---|
| 管理后台 | `https://lh.y-98.cn/admin`，公网可达 |
| 管理员凭据 | 单一 OWNER 账号，密码 `123123`（6 位连号，可在字典/暴力攻击首位命中） |
| 防护现状 | 匿名 `/api/admin/access` 401 正常；登录有限流（`scripts/verify-rate-limit.mjs` 覆盖）；无 2FA |
| 影响面 | 后台持有内容审核、财务退款、用户管理、AI provider 配置等权限；弱口令等于把以上能力暴露给爆破 |

风险结论：这是当前线上最大的单点安全缺口，修复成本远低于其风险，应尽快独立执行。

## 2. 目标与非目标

- 目标：生产管理员密码换成高熵随机值，旧密码立即失效，凭据进入密码管理器，全程留痕。
- 非目标：不新增管理员账号、不改权限模型、不动 JWT/会话机制、不上线 2FA（列入后续加固）。

## 3. 可选路径对比

| 路径 | 说明 | 结论 |
|---|---|---|
| A. 后台 UI 改密 | 管理员登录后台，在账户设置中修改密码，走应用自身的 bcrypt 校验与写入 | **推荐主路径** |
| B. `npm run admin:bootstrap` | 只负责把已注册邮箱初始化为 OWNER 角色，**不能修改密码** | 排除，不要误用 |
| C. 直接改库 `password_hash` | 绕过应用校验与审计，还需自备 bcrypt 哈希 | 不推荐；仅当 UI 路径不可用时作为兜底，须停写窗口 + 事前备份 + 双人复核 |

## 4. 推荐执行流程（路径 A）

1. **准备**
   - 密码管理器生成 ≥16 位随机密码（大小写 + 数字 + 符号），禁止任何可猜测成分；
   - 确认目标账号、恢复邮箱可达；
   - **先确定"密码丢了怎么办"**：当前没有服务端密码重置通道，一旦改密后丢失新密码将无兜底。执行前必须落实恢复手段（如：由 security-lead 持有密封的应急凭据，或先补一个受控的第二管理员账号）。
2. **执行前检查**
   - 在测试环境用同一版本代码预演一遍 UI 改密，确认改密后既有会话/JWT 是否被吊销（该行为依赖代码实现，执行前核实，本方案不预设）；
   - 执行时刻选低峰，避免与其他发布叠加。
3. **执行**
   - 管理员登录 → 修改密码 → 强制登出 → 用旧密码登录一次（应失败）→ 用新密码登录（应成功）；
   - 全程截图或留日志，写入操作记录（时刻、执行人、验证结果）。
4. **收尾**
   - 新密码仅存密码管理器，不进仓库、不进文档、不进聊天记录；
   - 操作记录中只记录"已轮换"，不出现密码本体。

## 5. 风险与回退

- 改密失败/中断：UI 路径失败即保持旧状态重试，无数据风险；
- 新密码丢失：走第 4.1 步预设的恢复通道；通道不存在时只能走路径 C 兜底（停写 + 备份 + 双人复核）；
- 会话未吊销的残留风险：若核实发现改密不吊销既有会话，改密完成后手动在后台登出全部会话（如后台支持），否则记为遗留项并排期；
- 与 M3 上线的关系：**不并入发布窗口**，独立执行，避免一次变更叠加两个变量。

## 6. 后续加固建议（按优先级）

1. 管理员密码强度校验（后端拒绝弱口令）；
2. 后台登录失败锁定与告警（现有限流之上）；
3. 第二管理员账号 + 最小权限角色拆分（`admin_roles` 体系已支持），避免单点；
4. 管理敏感操作审计留痕的定期核查；
5. 2FA/TOTP 评估；
6. 轮换周期制度化（建议 90 天，纳入 roadmap W 阶段检查项）。

## 7. 执行审批

| 角色 | 职责 |
|---|---|
| team-lead | 批准执行窗口、确认恢复通道已落实 |
| security-lead | 复核密码生成与保管方式、验收轮换结果 |
| devops-lead | 执行操作、留痕、验证新旧密码失效/生效 |
