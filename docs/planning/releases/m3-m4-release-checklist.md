# M3+M4 合并上线 vs 分两次上线：批次对照（供拍板）

> 结论先行：**建议 M3+M4 一次窗口合并上线（47 条迁移同批），随后直接进入 M5 灰度观察期**，即 `m5-pilot-runbook.md` 的"情形 2"路径。理由见 §3。
> 拍板人：项目总负责人。本文档只做利弊对照，不替代发布批准。

## 1. 两个方案的定义

| 方案 | 内容 | 对应 runbook |
|---|---|---|
| 方案 A：一次窗口 | M3 数据模型/回合编排 + M4 闭环/worker + 2 条迁移（45→47）一个发布窗口全部上线，窗口后进入灰度观察 | `m5-pilot-runbook.md` 情形 2（C4 执行迁移） |
| 方案 B：两次窗口 | 第一次窗口按 `m3-launch-runbook.md` 先上 M3（2 条迁移 + M3 代码），观察后再开第二次窗口上 M4/M5 | `m3-launch-runbook.md` + 第二次增量窗口 |

## 2. 逐项对照

| 维度 | 方案 A：一次窗口 | 方案 B：两次窗口 |
|---|---|---|
| 迁移风险 | 2 条迁移均**纯增量**（6 张 story 表 + 1 张埋点表，不 ALTER 既有表），副本演练已断言 countsPreserved/integrity/foreignKeys；一次性应用与分两次应用风险无本质差异 | 相同；第一次窗口已把迁移做掉，第二次窗口无迁移 |
| 回滚位 | `c4-rc2` 补齐 47 迁移目录后可直接切回（新表留着不用）；一次窗口 = 一次回滚语义，简单 | 第一次窗口回滚语义同样成立；第二次窗口回滚目标是"M3 版应用"，但**该版本目录需要额外保留与验证**（`c4-rc2` 不含 turns 端点，M3 期间创建的实例在 c4-rc2 上 409） |
| 功能完整性 | 上线即闭环：worker 整理、结章、失效、恢复全部就位；storyStatus 不出现长期 PENDING 半功能态 | 第一次窗口后 worker 不存在，状态整理永远 PENDING——M3 独立上线的"稳态"其实是**半功能态**，第 27 章要求"不将无上下文的回复伪装为连续剧情"，灰度观察指标（四比率、状态健康度）在两次窗口之间无法有效采集 |
| 打包可行性 | `pack-release.mjs` 打当前工作区，HEAD `ed0cd03` 即发 | 需要回退到 M3 时代提交重新打包验证，引入"历史重建"这一新风险源；或第一次窗口也发全量代码但只迁移 2 条——那与方案 A 无差别（M4 worker 依赖 turns 编排，拆不开） |
| 窗口次数与成本 | 1 次停写窗口（30–60 分钟） | 2 次停写窗口 + 2 套备份/断言/观察 + 窗口间隔期的双版本维护 |
| 观察与灰度 | 窗口后立即进入灰度观察期，指标基线干净（同一版本上采集全程数据） | 两版本间指标不可比；M4 上线后观察期还要重新归零 |
| 主要风险点 | M4 worker 与前台写入共享单库（SQLite 锁竞争）首次在生产暴露 | 两次生产变更 = 两次暴露机会；且第一次窗口的"半功能态"本身是新增的用户可见风险 |
| 风险缓解（方案 A） | `STORY_WORKER_DISABLED=1` 已实现：worker 异常时停 worker 保站点（runbook §6 E1）；灰度旗标（story-rollout-flags.md F1–F3）实现后可进一步关写入 | 需维持两套 runbook 与两个回滚位 |

## 3. 建议

**方案 A（一次窗口合并上线）**，理由按权重：

1. **M3-only 不是可独立验收的稳态**。M4 worker 是让 storyStatus 从 PENDING 落定到可用状态的关键；没有 worker 的 M3 上线，用户创建的实例永远停在"整理中"，等于把半成品暴露给试点用户，违反规划书"不伪造成连续剧情"与"验收者能复现关键路径"的要求。
2. **拆包成本是纯新增风险**。打包脚本基于当前工作区，回退历史打包需要重新走一遍构建/演练验证，收益为零。
3. **迁移风险不随拆分下降**。两条迁移纯增量、副本演练已通过，SQLite 单条迁移事务化，失败自动回滚。
4. **降级手段已就位**。worker 有 `STORY_WORKER_DISABLED=1`（提交 `ed0cd03`），runbook §6 E1–E6 覆盖了"先关 worker/写入再切回旧应用"的全部降级路径；c4-rc2 回滚位补齐迁移目录后可随时切回。

**附带条件**（采纳方案 A 时建议同时批准/执行）：

- 窗口前完成 `STORY_RUNS_DISABLED` / `STORY_TURNS_DISABLED` / `STORY_CLOSE_DISABLED` 三个旗标的实现与测试（story-rollout-flags.md §2），否则 F1–F3 只有手工停写兜底；
- 生产管理员密码轮换（`admin-password-rotation-plan.md`）在窗口前完成——HANDOFF §6 既有安全缺口，优先级高于功能发布；
- 试点名单（8–12 人）与告警责任人窗口前冻结。
