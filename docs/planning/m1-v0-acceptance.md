# M1 / V0 验收测试方案

> 范围：纯前端体验层（场景卡、三条建议动作、章节结束页）。不新增数据库表，不假设存在 story/chapter 相关 API；新体验断言以页面 DOM 为主，持久化/授权断言只使用现有 /api/conversations 系列。此方案新增的测试清单是规划，不在本次修改中创建测试代码。

## 测试现状与约定

- npm test 执行 tests/runner.ts，注册 roleplay markup、Tier 1–4 套件，由 runner 汇总通过/失败用例数。历史记忆中的“160 项断言”不是当前固定承诺；每次记录实际输出的 summary 数值，不预设总数。
- Playwright 验收脚本位于 scripts/verify-*-browser.mjs。现有脚本用 assert/strict、可访问名称/DOM 定位、逐条 PASS 输出及 checks 数组计数；失败时尽力保存 failure 截图，部分脚本另写 result JSON。矩阵实例读 .next-build 构建产物，需先 build。
- scripts/run-browser-matrix.mjs 参数以扩展名区分：文件路径（.mjs/.cjs/.js/.ts/.tsx）执行 node --import tsx <path>；否则按 package.json script 名解析命令。脚本串行共享一个隔离库和服务，禁止并行跑相互影响的矩阵项。可用 MATRIX_KEEP_ARTIFACTS=1 留存矩阵产物。
- 可复用的 HTTP helper：tests/helpers/test-client.ts 的 TestClient（鉴权、请求、JSON、SSE drain）。矩阵使用 tests/helpers/seed-http-fixtures.mjs 准备 HTTP fixtures；需要专用临时库时参考 scripts/helpers/create-isolated-db.mjs，不得碰开发/生产库。当前 scripts/helpers 未发现通用 Playwright helper；浏览器脚本沿用现有模式自行创建 Chromium、locale/viewport、page、PASS 计数、错误收集和截图目录。

## 验收矩阵

每条“步骤”与“可观察结果”均应独立断言；文本具体值应来自批准的 V0 fixture/config，不在测试里发明产品文案。浏览器关键流程在桌面和窄屏至少各跑一轮；组件覆盖断点与空状态按对应项执行。

| ID / 风险 | 层 | 操作步骤 | 可观察结果（通过条件） |
|---|---|---|---|
| SC-01 合格场景呈现 | 浏览器 | 打开一条有完整审核身份、冲突、目标文案的角色详情。 | 首屏 DOM 同时可见三项内容，无需展开；从可交互时刻起 3 秒内可读；角色/目标关联正确，无缺项占位。 |
| SC-02 开始不自动发消息 | 浏览器 + HTTP | 从场景详情点击开始；检查进入的角色/会话；读取该会话消息。 | 进入对应角色的聊天开场；开始动作本身没有创建 USER 消息或 POST 消息请求；会话通过现有 GET /api/conversations（或其详情/消息读取端点）可定位。 |
| SC-03 缺配置不伪造 | 浏览器 | 打开缺少身份、冲突或目标之一的角色入口；再通过旧链接进入自由聊天。 | 不展示不完整/臆造的场景卡、不提供 V0 场景开始动作；原自由聊天仍可进入和输入。 |
| SA-01 恰好三条建议 | 浏览器 | 进入配置完整的场景聊天开场，统计建议动作控件。 | DOM 中恰有三条建议；文本/ID 对应该场景已审核配置；自由输入和发送控件同时可用。 |
| SA-02 选择只填入 | 浏览器 + HTTP | 点击一条建议，监听消息 POST；读取输入框值及现有会话消息。 | 建议文本被填入输入框；没有 POST、没有新增 USER 消息，也没有独立 AI/计费请求。 |
| SA-03 可编辑、清空、改选 | 浏览器 | 选建议，改写内容；清空后再选择另一条。 | 输入框反映每步操作；仍可自由键入；每一步单独检查，不触发发送。 |
| SA-04 明确发送才保存 | 浏览器 + HTTP | 选择建议后点击发送；drain SSE，再读该会话消息。 | 只有发送后才出现一条 USER 消息；其正文等于用户最后编辑后的内容；请求完成后流正常结束，列表/历史一致。 |
| SA-05 无建议配置降级 | 浏览器 | 打开无建议配置的 V0 开场并尝试自由输入、发送。 | 不出现通用伪建议；自由输入可用；消息正常保存。 |
| SA-06 失败与重复提交 | 浏览器 + HTTP | 模拟消息请求失败；再触发连续/重复点击发送。 | 显示错误、草稿保留且发送控件恢复；失败不计成功消息、不重复写入；恢复网络重试后仅保存预期消息。 |
| SA-07 首条消息时延 | 浏览器 + HTTP | 从开场变为可交互时开始计时；走一遍新用户首条消息发送并确认保存。 | 分别记录动作耗时和成功保存时刻；成功首条 USER 消息在 30 秒内才满足目标；选中/输入/失败均不算。此为流程时间指标，不以总消息量作判定。 |
| EN-01 主动结束展示 | 浏览器 | 在有已保存消息的会话中主动点击结束/暂时离开。 | 进入结束页；由用户动作触发，无自动结束；结束页 DOM 标识与来源会话一致。 |
| EN-02 真实片段 | 浏览器 + HTTP | 结束前确认会话中有独特的真实 USER/ASSISTANT 消息；结束后检查片段。 | 结束页引用的每段文字可在当前授权会话既有消息中找到，角色/顺序一致；片段不是新生成或其他会话内容。 |
| EN-03 无消息空态 | 浏览器 | 对无消息会话触发结束。 | 显示“暂无可回顾片段”类明确空态并提供返回，不出现虚构摘要。 |
| EN-04 未完成问题依据/空态 | 浏览器 | 用含审核问题依据的 fixture 结束；另用无依据 fixture 结束。 | 有依据时只展示可追溯原文或审核内容；无依据时出现明确无整理问题空态；不把推测、承诺、完成状态写成事实。 |
| EN-05 返回同一会话 | 浏览器 + HTTP | 在结束页点击回到原会话；读取当前 URL/页面及会话消息。 | 打开同一 characterId、同一 conversationId，原有消息仍在；返回动作不新建会话、不改写历史。 |
| EN-06 下一章入口条件 | 浏览器 | 分别打开无已发布后续内容、有有效后续内容的结束页。 | 无后续内容时不存在失效入口；有后续内容时入口可见且点击后导航到有效现有页面/内容，不检查或依赖 story API。 |
| EN-07 临时结束、不持久化 | 浏览器 + HTTP | 结束后刷新/重新打开旧会话；通过现有会话 API 检查会话字段和消息。 | 不出现持久章节完成状态、结果或解锁；消息/会话既有数据未被额外改写；旧会话仍可访问。 |
| EN-08 加载失败与无权访问 | 浏览器 + HTTP | 模拟结束页读取失败；再用另一账号打开该会话链接/现有消息读取端点。 | 失败显示重试/返回；未授权请求按既有 API 行为拒绝，页面不泄露对方消息或片段。 |
| EN-09 刷新与窄屏 | 浏览器 | 刷新结束页/旧会话深链；在项目既有手机 viewport 检查布局。 | 深链仍回到原会话；关键按钮可操作、文本不重叠/无横向溢出；无 pageerror。 |
| RG-01 旧聊天与额度 | HTTP + 浏览器 | 走旧角色链接进入自由聊天并发一条消息；检查原额度行为。 | 旧流程可用；额度/余额响应沿用原行为；V0 选择建议或打开结束页不额外触发收费/消耗。 |

## 回归范围与必跑命令

只验证 V0 风险直接相关的既有面，不做“全站回归”：旧自由聊天与历史、/api/conversations 系列、历史编辑/重生成、限流、额度、i18n 路由。

1. npm test：HTTP 主套件，检查会话/消息交叉功能及 runner 实际汇总。
2. npm run test:conversations:messages 与 npm run test:conversations:service：现有消息/会话 API 与服务行为。
3. npm run test:m1:history：历史及编辑/重生成相关既有浏览器行为。
4. npm run test:rate:limit：限流边界。
5. npm run test:m4:budget-guard：额度/预算守卫行为；另在旧聊天 UI 回归中核对现有额度提示不变。
6. npm run test:middleware:locale：i18n 路由中间件。
7. npm run build：产出矩阵所需 .next-build（按项目配置）；其后以文件路径执行新增浏览器脚本：MATRIX_KEEP_ARTIFACTS=1 node scripts/run-browser-matrix.mjs scripts/verify-m1-v0-browser.mjs。矩阵报告同时确认使用隔离 DB、脚本 PASS 数、退出码及截图产物。
8. 若 V0 改到旧自由聊天/会话浏览器共用组件，补跑 npm run test:browser:matrix -- test:browser test:m1:history；不因本方案默认要求整个默认矩阵。

命令是否能直接通过依赖项目已安装依赖、测试服务/环境变量和当前构建配置；执行记录须写出实际命令与退出码，不把环境未就绪记作产品通过。

## 证据与失败分类

每次交付保存一份可追溯记录：commit/build 标识、环境（隔离实例 URL、Node/浏览器版本、viewport、locale、是否 mock AI）、逐字命令、每条退出码、开始/结束时间；HTTP 测试 summary 的 passed/failed/total；浏览器逐条 PASS/SKIP 及数量、矩阵结果；截图相对路径（成功关键状态和失败截图）、必要的 result JSON；失败时附相关请求 method/path/status、脱敏响应摘要、浏览器 console/pageerror。不得保存聊天正文、草稿、令牌或个人数据作为证据；使用专用合成 fixture，截图需避免暴露真实资料。

失败先隔离“脚本失配”与“产品回归”，不以快速改断言文案绕过：

- 脚本/fixture 过期的可能证据：预期元素/文案/选择器不存在，但对应功能可通过当前界面手工确认；页面结构或审核 fixture 已变化；API 请求成功且数据状态正确，仅断言定位旧文案失败。先核对当前产品规格、DOM/accessibility tree、响应与 fixture，确认测试意图仍成立后才更新脚本定位/文案，并保留原失败证据与修订理由；不得只把期待文本改成当前文本就结案。
- 真实回归的判据：规格要求的交互/状态缺失；错误请求、状态码或保存数据违反既有契约；建议点击触发发送/计费、消息不持久化、内容/权限泄露、空态或失败恢复缺失、旧流程受阻；在独立复现且正确 fixture 下仍失败。按行为缺陷登记，修实现并重跑失败用例与相关回归。
- 环境/基础设施问题：隔离服务未起、构建缺失、测试账号/fixture 未准备、浏览器无法启动等，记录为 blocked/inconclusive，不记产品通过，也不通过修改产品断言掩盖。
- 修订/修复后重跑原失败项，并重跑受影响回归命令；证据需能关联首次失败、根因分类、改动 commit 与重测结果。

## 通过门槛

所有适用的 V0 矩阵项通过；失败/跳过均有解释，关键体验项不得无故 skip；上述必跑回归命令全绿；无未解决的严重权限、数据完整性、消息误发/误扣额度问题；首条消息时间按定义达标并报告样本与计时口径。发布结论附残余风险与证据链接。

**V0 不得用总消息数上升作为通过条件。**
