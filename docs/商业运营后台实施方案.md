# 星伴商业运营后台实施方案

日期：2026-10-13。依据用户最新要求，将现有管理入口扩展为完整商业运营后台。当前只是已上线的审核/财务界面和权限入口，不能标记为商业后台完成。以 PC 的表格、筛选、批量操作和工作流为主，移动端支持查看及常用操作。

## 产品边界

后台统一管理站点业务、AI 接入、支付商户、运营内容、权限及运行状态。先按一个品牌站点、多个运营角色实施；不默认改成多租户 SaaS。

后台新增前端内容指创建角色、圈子、横幅、公告、分类、导航项和由已支持组件组成的页面。必须有组件类型、字段校验、预览、草稿、发布、定时生效和版本恢复；不能承诺后台凭空新增数据库业务、支付协议或任意执行前端代码。新的业务组件由开发实现，再进入可配置组件目录。不得通过输入 JavaScript、任意 SQL 或服务器命令充当页面搭建功能。

收费规则继续等用户模型成本和价格，不预设商业价格。真实模型/支付配置可管理，但真实计费调用和交易验收要单独记录。异地备份本机下载、PWA 打包仍按用户决定暂缓。

## 国际开源项目参照

以下是参考其职责划分的设计提议，不是已移植的功能，也不按开发者国籍判断质量。不整体替换当前项目；如后续复制源码或引入依赖，另核实该版本许可证和商业使用条款。

| 项目与官方资料 | 参考方向 | 本项目采用的设计 |
|---|---|---|
| [Dify](https://github.com/langgenius/dify) | 模型管理、AI 应用工作流、可观测性 | 供应商、模型、路由、成本及调用日志分开；运营配置不混入聊天路由 |
| [Payload 管理面板](https://github.com/payloadcms/payload/blob/main/docs/admin/overview.mdx)、[权限](https://github.com/payloadcms/payload/blob/main/docs/access-control/collections.mdx) | 内容管理、草稿预览、版本及权限 | 内容类型独立、编辑和发布分离，服务器同时检查读/写权限 |
| [Saleor](https://github.com/saleor/saleor) | 前后端分离的商业平台 | 支付与内容表现分离，订单/退款保持服务端权威 |
| [Medusa](https://github.com/medusajs/medusa) | 商业平台扩展与模块化 | 商业能力按模块提供服务，运营后台调用服务，不复制账本或供应商规则 |

## 功能矩阵与验收

| 编号/模块 | 需要实现的详细功能 | 完成证据 |
|---|---|---|
| CM01 权限与管理员 | 管理员列表、角色、功能权限、读/写/发布/退款/密钥管理区分、账号停用、会话撤销、审计；原环境管理员安全迁入 | 匿名/普通/不同运营角色越权测试，撤权立即生效，现有管理员保留 |
| CM02 用户与客服 | 搜索、分页、筛选、资料、注册/最后活动、账号状态、社区禁言与整站停用分别管理；订单/账本/角色关联查看；操作理由 | 只返回必要资料；不返回密码/令牌；状态转换及恢复有审计，停止账号不能继续敏感操作 |
| CM03 角色管理 | 草稿/待审/公开/下架列表、搜索标签、编辑、版权登记、预览、审核理由、批量审核、归属关系 | 私有角色不泄露；发布/下架影响发现和聊天可见性；并发编辑拒绝覆盖 |
| CM04 社区管理 | 圈子、成员、帖子、评论、图像附件、置顶推荐、内容下架、举报、申诉、禁言及审计 | 复用现有社区规则，权限和附件可见性完整验证 |
| CM05 CMS 与页面配置 | 品牌/Logo/主题、首页横幅、导航、分类、展示区、公告、固定页面、页脚；支持的页面组件库；草稿/预览/发布/定时/版本恢复 | 后台保存后前台按发布状态实际生效；无脚本注入；非法链接拒绝；回滚可核验 |
| CM06 AI 供应商 | 多供应商、协议类型、Base URL、密钥写入/替换/停用、连通性检查、启停、配置版本；浏览器仅见脱敏状态 | 密钥不返回、不入日志；供应商配置可保存并影响网关；错误配置不产生不可控调用 |
| CM07 模型与路由 | 模型名称/标识、供应商绑定、可用状态、默认/备用模型、角色可选范围、超时/重试/输出上限、健康记录 | 发送/重生成都使用同一服务配置；停用及降级实际生效；无静默改价 |
| CM08 AI 成本与额度 | 各模型输入/输出单价及币种/生效日期、预算、用量、失败/重试未知费用、用户额度、限流、告警 | 所有价格有来源和变更记录；未知费用不当作零；预算不是精确账单上限 |
| CM09 商户与支付渠道 | 商户编号、渠道类型、密钥/证书、回调域名、测试/正式环境隔离、启停、退款开关、配置检查 | 签名及权限验证；密钥不泄露；新旧订单使用明确配置版本；未知渠道结果不能自动补单 |
| CM10 充值与权益 | 已有三档套餐、上下架、排序、赠币活动、定时范围；后续经用户确认的会员/免费次数/扣币规则 | 订单价格快照、并发幂等和余额一致；不能直接编辑余额绕开账本 |
| CM11 订单与财务 | 分页/筛选订单、状态、回调处理记录、退款审批及执行、查单、财务对账、渠道账单/手续费、异常处理、受控导出 | 本地密钥与模拟渠道测试；实际商户验收另记；退款未知结果冻结和重试保留 |
| CM12 运营分析 | 用户增长/活跃/留存、对话/帖子/审核量、充值转化、退款、真实成本与毛利；时间范围、数据口径 | 真实数据查询，不显示伪造数字；样本不足或成本未知明确标注 |
| CM13 任务与增长 | 签到、任务、奖励、礼物、推荐位、公告和活动管理；满足条件与一次领取区分 | 奖励经经济模块事务入账，不能只改页面奖励文字 |
| CM14 系统与运维 | 服务状态、健康检查、告警设置、备份清单、恢复/回滚记录、证书状态、配置发布、维护模式 | 定时执行和告警送达分别验收；备份仅在用户指定位置；不能在网页执行任意 shell |
| CM15 合规与交付 | 政策/年龄/版权、保留期限、注销与导出、员工操作审计、权限说明、运维文档、真机/用户灰度 | 用户及运营确认、实际全流程记录和原 G0–G5 审查 |

## 代码责任和依赖

保持 Next/React 和已有业务模块，不把所有规则塞入一个 admin-service 或万能配置 JSON。

| 责任 | 归属与调用关系 |
|---|---|
| 管理员角色和能力判断 | `src/lib/admin/`；向各领域提供能力检查；页面仅展示服务器返回的能力 |
| 用户状态与资料 | `src/lib/accounts/`；社区禁言通过 `community` 的公开服务；停用与注销分离 |
| 角色/社区规则 | `src/lib/characters/`、`src/lib/community/`；原审核行为迁移时仅处理该工作流 |
| CMS/发布内容 | `src/lib/site-content/`；前台读取已发布快照，管理员编辑草稿；组件类型显式登记 |
| AI 配置/调用/费用 | `src/lib/ai/` 内分供应商配置、模型配置、网关路由、费用；既有聊天入口调用公开服务 |
| 商户/订单/退款 | `src/lib/payments/`；充值套餐与金币权威仍在 coins 模块；旧业务事务不复制 |
| 系统配置和密钥存储 | 小而显式的配置/密钥模块，数据库仅保存加密值或引用；加密主密钥留在受保护服务器配置 |
| 运维 | `src/lib/operations/`；可控任务与记录，不允许后台任意文件路径读取或执行命令 |
| HTTP/页面 | `src/app/api/<domain>/` 做输入、认证、服务调用、响应；后台路径 `/admin/<domain>`，UI 放 `src/components/admin/<domain>/` |
| 数据变更 | `prisma/schema.prisma` 与新有序迁移；先独立库迁移、现有数据保留检查，再备份和部署 |

配置拥有作用域、版本、生效状态和修改人；一个模块的配置更新只影响自己的运行服务。商户和模型密钥写入接口与读取接口不同，列表永不回显原值。商户变更不使旧订单失去验签/查单能力。管理员权限不能靠客户端按钮是否隐藏决定。

SQLite 当前为单机实际数据库，不因文件小就自动替换。商业并发扩展需要单独完成 PostgreSQL 数据迁移、统一限流和共享上传存储方案；未验证前不宣称支持多实例，也不把生产数据库直接 reset/db push。

## 构造顺序

1. CM01：先完成细分管理员权限、审计与现有管理员兼容迁移，明确后续各模块权限；基础后台布局已有。
2. CM02–CM05：用户管理、角色/社区管理、可发布站点内容及组件配置，逐模块做前后台闭环。
3. CM06–CM09：AI 供应商/模型/预算、商户渠道后台配置，接入现有网关及付款服务；不做只有表单、运行时仍读旧 env 的假配置。
4. CM10–CM13：统一商业订单/退款/套餐/权益/报表/奖励；未确认收费部分保留配置设计，不启用。
5. CM14–CM15：运维、安全、政策、实际渠道和用户灰度；逐项完成原门禁和交付。

每个模块先记录调用者、表/配置、状态转换、权限、审计和测试范围，再编码。完成必须包含接口、实际后台页面、运行时生效、错误反馈、隔离测试及必要的线上验收。新增菜单或输入框不算完成。金额、权限、密钥和内容发布边界优先；不新增与这些职责无关的通用框架。

## 当前状态

CM01 当前变更地图：审核/财务权限辅助函数和 admin/access 是认证调用方；角色、权限、运营人员关联及操作审计使用新有序迁移，不修改金币/订单字段。兼容原环境 ID 名单，数据库管理记录优先；初始化由受控命令显式指定已有用户为所有者，不把首个注册用户提升为管理员。财务读、套餐写、退款执行和审核读/写分别校验；管理员配置更改在事务内再次授权，拒绝最后一个所有者停用或降权。账户注销也检查该约束，非最后所有者注销停用其管理身份。新增权限及相关迁移先在隔离库验证，现有 admin 账号在部署阶段显式初始化。

整洁性清理先查框架入口、源码 import、脚本/CI、动态路径和文档引用。已移除无引用的上游 CONTRIBUTING/CODE_OF_CONDUCT 模板；许可证、素材来源、有效计划、当前架构/运维/安全文档、迁移、数据库和上传不按“看起来旧”删除。剩余候选代码随模块变更核实，不以扩大删除量作为验收。

本方案已建立功能范围和责任地图，国际项目资料仅为研究参照。CM01–CM15 的完整能力尚未完成；现有管理员/审核/财务入口和充值退款部分作为复用基础。CM01已在本地实现持久化角色、权限及审计，完成22项权限/注销/导出检查和Node24生产构建；新后台及既有入口各6组本机生产浏览器验收通过，支付/退款11项通过；服务器迁移尚未执行。CM02–CM15继续按上述依赖实施。
