# 后台功能生命周期与设置结构审查

日期：2026-10-23。目标：解决实际操作缺口，保持现有功能及前台数据关系，给后续扩展确定模块归属。真实收款、真实退款保持关闭。

## 1. 范围与证据边界

- 按 `packages/contracts/src/admin/nav.ts` 覆盖 25 个后台业务入口；查看对应管理组件、API 和领域服务，重点追踪删除、保存、引用、历史恢复、设置定位及权限。
- 改动前对线上 25 个入口及已有标签页进行了登录后的只读浏览器遍历：全部 HTTP 200，无浏览器运行错误或 HTTP 错误；该检查没有发出业务写请求。它只证明入口和标签可访问，不代表所有按钮都已完成写操作验收。
- 五类删除的状态、引用、版本、权限和审计用服务器临时 SQLite fixture 验证；测试自己创建数据库，不复制或修改运行库。
- 发布后的页面写入只针对本次新建的停用验收配置，删除这些配置后保留审计。设置搜索使用未保存草稿验证，不改现有运营参数。
- 本次不是“整个项目从此没有任何问题”的保证。未执行真实支付、退款、实际 AI 调用，也没有为测试而删除现有用户或历史数据。

## 2. 确证问题与本次处理

| 问题 | 处理 | 所属模块 |
| --- | --- | --- |
| AI 供应商、模型没有删除链路 | 增加受权限、状态、版本、引用校验保护的 DELETE 服务、接口和确认弹窗；返回引用数量 | `modules/ai/providers`、`modules/ai/models` |
| AI 编辑将读取结果直接摊入草稿，混入只读字段，服务端白名单拒绝保存 | 显式构造可编辑字段，不回传 `hasSecret`、关联供应商对象、引用统计等 | `components/ai-providers`、`components/ai-models` |
| 新建停用供应商仍强制填写密钥 | 未启用配置可不填密钥；启用时继续由服务器校验 | AI 供应商表单 |
| 增长任务、礼物、金币套餐无法清理未用配置 | 增加安全删除；有历史记录只停用/下架 | `modules/missions`、`modules/gifts`、`modules/coins` |
| 礼物存在旧式字符串关联，单查目录 ID 会漏历史 | 同时检查 `Gift.catalogId` 和 `catalogId=null + giftType=code` | 礼物目录服务 |
| 内容版本恢复把 JSON 字符串交给再次序列化的 API 客户端 | 改为传原始对象，消除双重编码 | `components/site-content` |
| 删除失败信息在背景页，弹窗里看不到 | 在删除弹窗及 AI 编辑抽屉内显示错误 | 各对象所属组件 |
| 关闭/切换编辑会丢草稿 | AI 抽屉、任务编辑、礼物和套餐切换增加未保存确认；保存中禁止关闭 | 各对象所属组件 |
| 礼物保存成功但刷新失败后仍留在旧版本草稿 | 保存成功先结束编辑；刷新失败单独提示，避免误导重复提交 | 礼物目录组件 |
| 套餐保存后刷新失败不能明确区分 | 保留旧列表，明确显示“已保存但刷新失败” | 财务套餐组件 |
| 设置中心一类内参数过度平铺 | 小节目录、单小节内容、常用/高级分层、全局搜索定位 | `components/settings` |
| 跨分类搜索在新分类数据加载前提前消费聚焦请求 | 等待对应数据及实际输入控件渲染完成再聚焦，并加入浏览器回归脚本 | 设置面板 |
| 管理角色几十个权限同屏平铺 | 按业务折叠、名称/技术键搜索、已选计数；不改变授权定义 | `components/operators/permission-picker.tsx` |
| 新增模型引用展示可能随调用历史增长而拉取大量记录 | 会话与 AI 调用按数据库分组统计，不加载完整历史 | AI 模型服务 |

## 3. 删除语义与历史保护

| 对象 | 允许物理删除的条件 | 拒绝删除后如何处理 |
| --- | --- | --- |
| AI 供应商 | 已停用，所属模型数为零 | 先迁移/处理配置模型；有历史关联的模型保留，供应商保持停用 |
| AI 模型 | 已停用、非默认、非备用；无角色绑定、会话绑定、成本价格、金币价格、AI 调用、任务模型设置引用 | 调整运行配置；历史存在时保留停用，不清理历史来强行删除 |
| 增长任务 | 已停用，无 `UserMission` 领取记录 | 保留停用，历史奖励和领取记录不变 |
| 礼物目录 | 已停用，无目录 ID 或旧式代码关联赠送记录 | 保留停用，赠礼历史与原价不变 |
| 金币套餐 | 已下架，无支付订单快照关联 | 保留下架，已下单金额和金币快照不变 |

通用规则：界面说明影响、填写理由、显式确认；服务器重新检查管理权限、当前版本和引用；检查、删除及写审计在同一事务内完成。按钮禁用不是安全边界，绕过界面直接调用接口仍被校验。删除不能级联清理业务历史。

固定参数登记项不提供“删掉参数定义”的普通操作。需要恢复默认值时使用现有恢复流程；需要关闭功能时使用业务开关。会员月/季/年方案保留启停，不删除已购买权益快照。

## 4. 全部入口的生命周期判定

这里区分已有能力、缺口和不适宜的操作，不把“没有 DELETE 接口”一律列为错误。

| 入口 | 当前合理能力及本次判定 |
| --- | --- |
| 工作台 | 指标与入口，不是可删除业务对象 |
| 用户管理 | 资料、资产详情、封禁/解封、撤销会话；注销需走账户领域流程，不能删除账务关联身份行 |
| 角色管理 | 编辑、发布/下架、素材和模型绑定；未使用草稿归档可作为后续专题，有会话/收藏/赠礼不能普通删除 |
| 审核中心 | 状态处置、举报/申诉处理；处置证据与审计保留 |
| 圈子与成员 | 已有隐藏/恢复及成员管理；不是缺失删除错误 |
| 帖子管理 | 下架/恢复及内容软删除，保留引用与审计 |
| 评论管理 | 隐藏/恢复/清除内容，保留举报及关系记录 |
| 评理广场 | 关闭、隐藏及奖励处理；投票、争议、金币记录不能普通删除 |
| 站点内容 | 草稿、丢弃草稿、发布/下架、版本恢复；本次修复恢复请求编码 |
| 他眼中的你 | 结果管理已有删除接口；配置与结果分别归属玩法模块 |
| 活动奖励 | 本次新增未使用任务和礼物删除；签到档位仍整体校验保存 |
| 运营分析 | 聚合只读，不对统计结果增加删除 |
| 模型服务 | 本次补齐安全删除、依赖展示、编辑字段与抽屉反馈 |
| AI 供应商 | 本次补齐安全删除、依赖展示、编辑字段与抽屉反馈 |
| 价格与成本 | 采用生效时间/版本；历史成本与币价不普通删除 |
| 财务支付 | 本次补齐未使用套餐删除；订单、退款、回调、对账保留 |
| 会员方案 | 月/季/年价格、权益和退款参数保持统一配置；购买与退款历史保留 |
| 支付商户 | 启用状态、凭据与版本管理；有支付关联不能普通删除，收款仍关闭 |
| 设置中心 | 本次增加细分目录与全局定位，恢复默认/历史/导入导出保持 |
| 后台任务 | 执行、日志、运行参数；不能通过删除任务记录来撤销业务结果 |
| 通知统计 | 聚合只读；通知保留策略应归通知领域，不能当报表删除 |
| 系统运行 | 维护、证书、备份和任务状态；备份清理由保留策略负责 |
| 管理员与角色 | 管理身份启停、角色新增/编辑/授权；本次改善权限选择。未分配自定义角色删除列为后续专题，系统角色保留 |
| 操作审计 | 只读证据，不提供普通删除 |
| 注册合规 | 年龄确认、协议和政策版本；版本历史保留 |

## 5. 设置中心信息架构

不改 `packages/contracts/src/settings/registry.ts` 的键、分组、默认值、验证及前台消费接口。仅重组展示，避免一次界面优化变成参数迁移。

- 聊天与内容：聊天输入、帖子、评论、角色、上传、行为频率。
- 计费与额度：基础收费、结算口径、剧情入口收费、剧情运行、成本换算、AI 任务预算。
- 增长与玩法：赠送规则、邀请/新手、他眼中的你入口/购买/内容、评理入口/结案、聊天记忆、后台任务。
- 账号运行：注册和登录会话等独立小节。
- 提示词：按实际业务模板划分。

107 个可见登记项各归一个小节；另 5 个隐藏的任务模型路由参数仍由价格与成本专页维护，有相应查看权限才显示跳转。搜索可用中文名称、技术键、说明和所属分类定位；同类切换保留草稿，跨类/离页提示放弃。搜索高级项可直接展示并聚焦，不要求用户先猜折叠位置。

## 6. 后续扩展规则与分阶段计划

### 模块归属（本次遵循）

1. `apps/admin/src/components/<业务>`：列表、详情、编辑、删除交互，不直接访问数据库。
2. `apps/api/src/app/api/admin/<业务>`：会话、请求/响应适配，调用所属领域服务。
3. `packages/backend/src/modules/<业务>`：状态、权限、引用检查、事务和审计，业务规则的唯一所有者。
4. `packages/contracts`：跨端参数定义、权限、路径及纯数据，不引入服务器依赖。
5. `packages/ui` 和后台 `layout`：通用外观与交互，不持有某个业务的状态规则。
6. `tests`：每个新增生命周期同时写服务行为测试与关键交互验收；新设置必须有分类覆盖测试。

### 优先级

- 本次交付：五类配置安全删除、AI 编辑修复、CMS 恢复修复、设置分层搜索、草稿/错误反馈、权限选择分类。
- 后续第一阶段：设计可复用的“停用/归档/恢复”产品规范，明确归档后默认列表隐藏、可筛选恢复、引用可追溯。优先评估未分配自定义管理角色、未使用角色草稿、旧商户配置；先明确迁移及恢复规则，不直接添加一个无语义的全局删除按钮。
- 后续第二阶段：统一列表筛选、分页、空状态、批量操作影响预览；引用信息支持跳到关联对象，按权限裁剪链接。
- 后续第三阶段：新业务按领域独立子目录扩展，登记导航、权限、设置归属、前台消费者、状态转移、审计和测试。只有出现真实共享需求时才提取公共层，不为了“像大型项目”制造空目录或万能模块。

每阶段验收须分别列出：代码检查、隔离行为测试、线上真实操作、未覆盖分支。涉及真实收款、历史回滚或数据结构迁移，另行确定范围，不随界面改造自动执行。

## 7. 发布与验收记录

使用项目既定 server-first 流程：核对服务端源文件哈希 → 在服务端应用补丁 → 服务端类型/专项/架构检查 → 构建相关 API 和后台 → 切换构建 → 线上验证 → 同步 GitHub。无需重建未改动的前台应用，无数据库迁移。

最终结果、构建标识、线上操作与限制见同目录 `validation-admin-functional-20261023.json`。不要把本报告中的后续规划读作已经完成。

发布后实测补充：五类新建停用配置已通过页面删除，临时配置没有残留；审核会话已撤销。最终 14 项专项测试通过。跨分类定位问题由额外线上操作发现并修复，修复后浏览器回归通过。

支付开关核对：运行库收款策略为关闭，四个运行子进程的 `EZFP_ENABLED` 和 `EZFP_REFUNDS_ENABLED` 均为 `false`。已有商户版本中仍保存退款支持选项，但运行总开关阻止真实退款；本次没有更改商户凭据、历史版本或任何支付开关，也没有发起支付/退款请求。
