# M4-01 收费方案草案 v0.1

更新：2026-10-13（Asia/Tokyo）。状态：充值三档已按用户确认纳入初始化，套餐与赠送活动后台已实现；每日免费次数和对话扣币仍是未启用草案，模型成本待确认。

## 1. 第一版收费方式

采用“每天免费次数 + 一次性充值金币”。先只上线一种聊天计价，不做会员、自动续费、创作者现金分成或按 Token 向用户计费。用户看到固定金币价，平台另外统计真实模型调用成本。

建议先保留一档标准模型；待成本确认后再决定是否提供不同价格的模型。模型备用链只允许切换到属于同一收费档、已确认成本的模型，不在调用过程中临时加价。

## 3. 建议规则：后续直接改这张表

| 参数 | 草案值 | 说明 |
|---|---|---|
| 对话收费开关 | 关闭 | 确认定价、实现及验收后才能开启 |
| 每账号每日免费次数 | 10 次 | 所有角色、发送和重生成共用；不结转 |
| 标准模型每次价格 | 1 金币 | 免费次数用完后按次付费；价格待成本核算 |
| 免费次数扣减时点 | 完整回复成功保存后 | 发起时先占用，防止并发超领 |
| 金币扣留时点 | 调用模型前 | 服务端核对余额，余额不足不调用模型 |
| 金币最终扣费 | 完整回复与账务事务成功提交 | 一次业务请求只收一次 |
| 失败、断流、保存失败 | 释放免费占用或返还扣留金币 | 不完整回复不算完成服务 |
| 用户主动取消 | 完成提交前取消则返还；提交后不返还 | 以服务端持久化状态判断，不依赖页面是否显示完成 |
| 重生成 | 与发送同价同规则 | 成功替换后结算；失败保留旧回复 |
| 新用户初始金币 | 建议 0 | 替代当前 100；保留已有账户余额 |
| 每日调用硬上限 | 先保留现有 200 | 独立于免费额度，充值不能突破；失败也计次数 |
| 重置时间 | 先沿用 UTC 00:00 | 北京时间 08:00；页面展示重置倒计时，后续可统一调整 |
| 签到/任务金币能否聊天 | 建议可以 | 先不拆多种钱包；必须计入运营赠送成本 |
| 金币有效期 | 第一版不设置自动到期 | 不做余额自动清零 |

示例：当日先成功聊 10 次，用完免费额度；再成功聊 3 次，花 3 金币。第 14 次超时，返还预扣的 1 金币，但该次仍占调用硬上限。重生成也按一次计。

## 4. 充值套餐占位方案

用户确定首批三档为 6 元 60、10 元 100、30 元 300 金币，无默认赠送。初始化创建新的人民币套餐，不覆盖后台后续编辑；原未配置人民币价格的种子套餐下架但保留记录。真实支付仍由商户配置及开关控制。

| 确认首批套餐 | 人民币价格 | 基础 + 赠送金币 | 按草案 1 金币/次估算的调用数量 |
|---|---:|---:|---:|
| 入门 | ¥6 | 60 + 0 | 60 次 |
| 标准 | ¥10 | 100 + 0 | 100 次 |
| 畅聊 | ¥30 | 300 + 0 | 300 次 |

仅当模型允许的输入历史、输出长度、重试策略确定后，才能判断这些价格是否可用。不能以“1 金币”推断平台每次只花固定 API 成本。

人民币价格最终写入 `priceCnyCents`，如 ¥6 对应 600 分。历史 `priceThb` 保留。订单锁定人民币金额和总金币，后续改套餐不改变旧订单。

财务管理员在 `/admin/finance` 可新增/编辑套餐、赠送金币、上架状态及活动开始/结束时间；不填时间则持续赠送，填写时间时结束时刻不再赠送。保留操作人及修改前后记录；旧页面报价变化会要求刷新确认。活动不改写旧订单。

## 5. 等成本资料回来后的核算方法

请按实际提供商、模型和币种记录：输入/输出每百万 Token 单价、缓存/其他费用、典型与长对话 Token 用量、失败重试费用、人民币结算成本及通道手续费。不要把模型名称或总 API 余额当作单价。

单次调用估算成本 = 输入 Token × 输入单价 / 1,000,000 + 输出 Token × 输出单价 / 1,000,000，再补充实际供应商其他收费。失败或重试产生的成本也必须记录；未提供 Token/单价时记未知。

三档基础套餐均为每金币 ¥0.10。若最终采用 1 金币/次，则名义单次收入为 ¥0.10，尚未扣退款、手续费、税费或免费额度成本；有赠送活动时按实际到账总金币重新核算。

核算应覆盖免费调用、签到/任务奖励、失败重试及服务器费用，不能仅比较付费请求的模型成本。各币种先分别核对；有真实汇率或结算记录后再做人民币核算。成本和费用不完整时不提供毛利率。

## 6. 账务实现方式

一次请求有一个服务端账务记录和客户端请求 ID。身份、内容、会话、操作和所选模型校验通过后，服务端决定用免费次数还是金币，不能接受客户端传入价格。

1. 在同一事务中检查硬上限、占用免费次数或扣留金币、建立请求记录；余额不足或配置无效直接拒绝，不调用模型。
2. 事务外调用模型并流式展示。自动重试和备用模型属于原请求，不重复扣免费次数或金币；供应商尝试成本另行记录。
3. 完整成功后，在同一事务中保存/替换回答、将占用转为已使用、确认扣费和请求完成。避免“回复已保存但账务显示失败”。
4. 失败时在事务中释放占用或追加返还流水，保留失败记录和供应商成本；不改写旧扣留流水。前端最终刷新余额、免费次数和聊天记录。
5. 同一请求 ID 并发或重放只处理一次；ID 与输入不一致时拒绝。同一失败请求重放不再次调用模型，用户主动再试使用新 ID。

核心状态为 `RESERVED → SETTLED / RELEASED`。不得仅因浏览器超时就重复退款。服务重启后的未结束请求，先核对回复与结算是否已提交；完成则保留扣费，无完成记录且确认执行已终止后释放。不能仅按超时时间释放仍在执行的请求。

请求保留当时的规则版本、金币价格、额度日期和模型档位；跨日失败释放原日期的免费占用，不给新日期额外加次数。改价只影响新接纳请求。

## 7. 模块与改动范围

| 所属模块 | 职责 |
|---|---|
| `src/lib/ai` | 模型白名单、供应商调用成本、现有调用硬上限 |
| `src/lib/coins` 新增对话计费服务 | 收费配置、免费占用、余额扣留/结算/返还、请求幂等；拥有账务事务 |
| `src/lib/conversations` | 发送/重生成业务流程及回复持久化，通过导出的计费服务配合事务，不复制计价规则 |
| 两个消息 API | 解析输入、认证、调用会话服务、映射 HTTP/SSE；逐步移出当前直接写库的发送/重生成逻辑 |
| 聊天与用量组件 | 展示免费剩余、金币余额、下一次价格、结果及充值入口 |
| 认证账户模块 | 仅将新注册赠币改为已确认规则，旧账户不变 |
| Prisma 新有序迁移 | 增加免费额度和计费请求/流水关联，不删除现有数据 |

模型硬上限与计费占用需在一个受控事务内组合，避免分两次提交造成额度和账务不同步。计费模块拥有结算事务，会话域通过明确的事务协作完成回复持久化，不能直接改计费表私有状态。

现有金币同时用于礼物、签到等业务，改动前核对这些调用者，保留其原有规则。商城、回调和退款继续使用现有支付域，不创建第二套钱包或支付实现。

## 8. 用户界面

- 输入框附近显示“今日免费剩余 3 次”，或“本次 1 金币 · 余额 25”。模型切换时同步获取服务端价格。
- 余额不足时显示充值入口，不开始模型调用；每日硬上限用完显示重置时间。
- 发起后显示处理中；完成后显示最终余额。失败显示“未扣费/已返还”，只有服务端确认释放后才承诺返还。
- 免费规则不由页面计算，日切、重启和并发都以服务端结果为准。
- 正式收费切换前公告开始时间、额度和价格；已有余额原样保留。

## 9. 实施顺序与验收

1. 用户补齐成本与套餐资料，确认第 3、4 节参数。方案可先改，不先开启收费。
2. 做新迁移与计费服务，在一次性隔离库验证免费、付费、返还和幂等。
3. 整合发送/重生成与成功持久化事务，接入价格及剩余额度展示。
4. 使用本地模型替身验证：最后一次免费额度并发、余额恰好够/不足、重复请求、断流、取消、保存失败、跨日、重启残留、运行中改价、备用模型与重生成旧回复保留。
5. 检查签到/任务/礼物与退款期间不能产生负余额；退款余额不足沿用现有拒绝规则，第一版仍只支持整单退款。
6. 类型检查、构建、隔离回归及浏览器完整旅程通过后，在测试环境启用；支付测试仅用临时本地密钥、mock provider 和隔离库。
7. 再完成真实商户沙箱与 G4，才开始小范围实付测试。

上线前需展示免费与价格规则，并将启用时间与规则版本留档。开关默认关闭；关闭后恢复原有仅硬上限的非收费聊天，不停止旧请求的结算或返还。回滚保留新表、新流水和用户余额，不删账。
